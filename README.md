# hive-data

The one async data-access layer every hive service goes through.

No service opens a database. A service calls a named operation, and where the
database actually lives is one configuration value in that process's
environment — so pointing the hive at a different database is an environment
change rather than an edit to anything.

Every mind and every service tracks `main`. There are no pinned versions to
carry per install, which makes the suite here a gate rather than an oracle:
nothing merges red, because `main` is what every service in the hive is
running.

## Install

```
pip install "hive-data @ git+https://github.com/danielstewart77/hive-data.git@main"
```

Upgrading needs `--force-reinstall --no-deps`, then a second pass over your
own requirements:

```
pip install --force-reinstall --no-deps \
    "hive-data @ git+https://github.com/danielstewart77/hive-data.git@main"
pip install -r requirements.txt   # resolve anything this package now needs
```

Both halves matter. The version in the metadata does not change between
commits, so pip clones the repo, resolves `main` to a new commit, compares
that unchanged version against what is installed and installs nothing —
`--upgrade` included, since the comparison is the version and not the commit.
And `--no-deps` means the day this package takes on a new dependency, a
service that ran only the first command is running code whose driver is
absent. In Docker the requirements layer is cached on the contents of
`requirements.txt`, so a rebuild reuses the venv holding whatever commit was
current when that file last changed: an `ADD` of the commit object busts that
cache, and the force-reinstall has to run *before* `requirements.txt` is
resolved.

## Use

```python
import hive_data
from hive_data import core

await hive_data.connect()          # once, at startup
session = await core.get_session(session_id)
await hive_data.close()            # once, at shutdown
```

`HIVE_DATABASE_URL` names the database. Nothing else is required; the pool
size and every deadline have defaults and are configuration when they need to
be (`HIVE_DATABASE_POOL_MAX`, `HIVE_DATABASE_STATEMENT_TIMEOUT`,
`HIVE_DATABASE_ACQUIRE_TIMEOUT`, `HIVE_DATABASE_TRANSACTION_TIMEOUT`).

### Async only

There is no synchronous face and no threadpool bridge to write. Two faces
would mean every query existing twice forever, and the sync one silently
blocking somebody's event loop the first time a service forgot the bridge.
Nothing in the hive needs a sync one: every consumer is already async at the
top, and those that once reached a sync `sqlite3` module through
`run_in_threadpool` did so precisely *because* the database layer was sync. That bridge comes out as each service
converts. Work that is genuinely CPU-bound — lucent's similarity scan over
vectors — belongs in `asyncio.to_thread` whatever the database is.

### Opening is explicit

Nothing opens a pool on demand. A lazy open under two concurrent first calls
builds two pools and holds double the connections against a ceiling shared
with every other service, with nothing reporting that it happened — so the
first operation against an unopened package raises `NotInitialised` and says
what was not done.

`connect()` also checks the applied schema against the columns these
operations name **and the identity sequences against the rows already in
their tables**, so a database that is not the one they were written against
is a process that refuses to start. The sequence check is what a bulk load
makes necessary: Postgres takes explicit ids on a `GENERATED BY DEFAULT`
column without advancing the sequence, so the next insert collides on a key
that is already there — and it collides as a uniqueness conflict, the one
outcome a caller is told is benign. A ledger recording nothing while
reporting a harmless duplicate is the mind answering with no record of
having been asked. A column this package names and the
database does not have would otherwise arrive as a missing dict key, and a
missing key reads as a value: `session.get("rotation_armed") or 0` is
"nothing armed" on the one column whose three states decide whether a
permanent session row is kept or retired.

## What an operation hands back

A row is a plain `dict`. Nothing a caller imports, nothing with methods,
nothing that stops being JSON when it crosses an HTTP boundary. A read that
matches nothing returns `None` — not an empty dict, which would be a row with
no columns — and a list read that matches nothing returns `[]`.

A **write reports how many rows it changed**, as `{"rows": n}`, with
`"row"` alongside it when the statement returned one. That is not
bookkeeping: it is the arbitration the hive already runs on. The contest
between two people sending a bot's claim phrase at the same moment is an
`UPDATE ... WHERE claimed_ref IS NULL` followed by a row-count test — that
statement *is* the arbitration — and the same shape decides whether a broker
message was newly inserted and whether a session still exists to report
context for. A write that could only answer with rows would answer `[]` to
every one of them, and `[]` reads as success: two confirmed owners for one
bot.

Columns a caller must ask for by name are withheld by default, and not only
on sessions. `minds.session_token` is the credential the gateway
authenticates to a mind with; `credentials.token_sha` is a bearer digest, and
reading it is how one holder authenticates as another; `users.password_hash`
is a password hash. On sessions, `carry_forward` is a composed system prompt
and `resend_content` a queued user message. All of those listings answer to
the service token every surface bot in the hive holds, so one careless
`SELECT *` publishes them to every bot. Pass `private=True` for the session
columns, or use the operation that exists for the one caller that genuinely
needs the value — `mind_session_token`, `credential_for_token`.

## Failures are told apart

A refusal reported as the wrong refusal sends somebody to the wrong machine.
`Unreachable` and `CredentialRefused` are two different hosts to go and look
at. `DatabaseMissing` means the server answered. `TimedOut` and
`NoConnectionAvailable` are neither of those — the database is up and serving
everybody else, and in the second case nothing was even sent, so nothing is
half-done and the remedy is this process's pool size. `Conflict` is separate
from `MissingReference` because the hive depends on the difference:
`add_message` is idempotent on purpose, since the SMS gateway re-POSTs the
same webhook on any non-2xx, so a duplicate reported as a generic rejected
write becomes a 500 and is retried forever.

`TransactionAborted` is its own outcome too: Postgres aborts a whole
transaction on the first error, so every statement after a handled failure is
refused without being read, and calling that a rejected write blames a write
the database never looked at while the real cause has already been caught.
Scope the recoverable part in a savepoint instead (below).

A timeout is classified by *where* it happened rather than by its class,
because the class cannot tell you: `TimeoutError` is `asyncio.TimeoutError`
and is a subclass of `OSError`. At connect time it is a host that never
answered and reports `Unreachable`; during a statement it is `TimedOut`. A
dead host reported as a timeout asserts the database accepted work it never
received, and sends the operator to the database instead of to the host.

Anything this package does not recognise is re-raised unchanged. A `NameError`
dressed as a `HiveDataError` is a bug wearing the costume of an outcome the
caller has a branch for, and the branch will swallow it.

## Units of work

One operation is atomic on its own. For a sequence, take a unit:

```python
async with hive_data.transaction() as unit:
    await unit.hold(f"session:{session_id}")
    await core.unbind_surface("terminal", "tile-1", unit=unit)
    await core.bind_surface(client_type="terminal", client_ref="tile-1",
                            session_id=session_id, unit=unit)
```

`hold` is what replaces the in-process `asyncio.Lock`es the gateway holds
today. Those are per process, and the only reason they sufficed is that comms
is the sole writer holding SQLite's read-write lock for the life of its
container — the exact property Postgres removes. The adopt sequence above is
a delete followed by a write; run twice concurrently without the lock it
leaves two active rows for one session, and the primary key catches nothing.

Inside a unit, this package's errors still apply. Translating only at the
transaction boundary would mean `except Conflict` around an operation passed
`unit=` does not fire — the exception escapes as a raw driver class and the
handler above it turns a duplicate into a 500, which is the retry loop the
taxonomy exists to prevent, reappearing inside the one construct that is
supposed to be safest.

For a failure the caller intends to recover from, scope it:

```python
async with hive_data.transaction() as unit:
    try:
        async with unit.savepoint():
            await core.add_message(..., unit=unit)
    except hive_data.Conflict:
        pass                      # already delivered; carry on
    await core.update_session(session_id, last_active=now, unit=unit)
```

Without the savepoint the second write raises `TransactionAborted` without
being read. The gateway's prevailing shape is try, log, carry on — which is
legal against SQLite and fatal against Postgres.

`hold` must be the unit's **first** statement, and is refused otherwise. A
hold placed after a read does not protect that read: two units both read an
unclaimed row, then both take the lock in turn, and both write. The method
would have been called correctly and still produced the outcome it exists to
prevent.

### A conversation lock without a transaction

A unit cannot be opened inside an async generator, and the gateway's
`send_message` is an async generator holding its conversation lock across the
yields — so the lock that most needs replacing is the one `Unit.hold` cannot
reach. `conversation_lock` is the same advisory lock at session scope:

```python
async with hive_data.conversation_lock(conversation_id, wait=False) as taken:
    if not taken:
        return "this conversation is mid-answer"
    ...
```

`wait=False` is the shape the gateway's turn lock actually has — a
non-blocking test that can *say* why it refused. Through a blocking lock that
check becomes a silent wait ending in a timeout, which tells the user
nothing. It pins a pooled connection for as long as it is held, which is
inherent to a cross-process lock, but it holds no open transaction, no
snapshot and nothing to roll back, and the lock is released explicitly rather
than left to the connection going back to the pool.

A unit refuses two things. It will not be **opened inside an async
generator**: `send_message` is a generator that writes to the database inside
its own loop over the model's response, so a unit opened there pins one
pooled connection for the length of a turn, and a closed browser tab abandons
the generator with the transaction still open, to be unwound whenever the
event loop's asyncgen finalizer reaches it. And it will not be **handed to a
second task**, because a transaction is one connection and sharing it means
each task can roll back the other's committed-looking work.

The generator check walks the whole stack rather than one frame, because a
guard that is right for one spelling gets read as proof the hazard is
handled — and the natural reaction to it firing is to move the write into a
helper, which is the same hazard one frame further out. It is still a
heuristic, and the transaction's own deadline is the real protection.

## Unpassed is not null

Optional parameters default to `UNSET`, and `None` means write null.
Collapsing the two can only express one of the two things the hive needs:
skipping every `None` never clears `harness_sid` — which has to be cleared so
a failed turn cannot resume a broken thread — and writing every `None` blanks
the context window to zero, which the surrounding code draws as a
conversation over its threshold.

## Column names are never a caller's

Values travel as parameters. Column names cannot: there is no placeholder for
an identifier. The gateway's dominant write assembles its `SET` clause at
runtime, so `update_session(**fields)` is the shape actually needed — and
every settable column is declared, with anything else refused as
`UnsettableColumn` rather than quoted and hoped for. An insert naming a
generated identity is refused too: Postgres accepts a value on a
`GENERATED BY DEFAULT` column without advancing the sequence, so the row
lands and the next insert collides. Round-tripping a row dict straight back
into an insert is how that happens by accident.

## Ordering

A ledger read orders by its identity column as well as by time, and the
identity is what breaks the tie. `session_turns.created_at` is whole epoch
seconds and `now()` is constant for a transaction, so two turns written in
one unit of work carry the same timestamp. An order without the tiebreak
returns them in whichever order the plan produced, and the visible failure is
the mind appearing to answer before it was asked.

## Memory search, without FTS5

`hive_data.memory` is the `memory` schema's own operations: `store`, `get`,
`delete`, `similar`, `keyword` and the blended `recall`. lucent still owns
being the memory service — it turns text into an embedding, decides the data
class and the tier, guards the standing tier, holds the knowledge graph and
prunes — and none of that moves here. What moves is the part that was
SQLite-specific, because neither half of it survives the move:

* **Vectors.** `memories.embedding` is a real `vector(4096)`, and similarity
  is cosine computed in the database. The dimension is declared rather than
  left open: a bare `vector` takes a row of any width and the mismatch then
  arrives at query time, on every recall. There is no approximate index —
  pgvector caps HNSW and IVFFlat at 2000 dimensions and `halfvec` at 4000, so
  an exact scan is the only option at this width. It is also the faster one:
  190ms warm over the live corpus, against a full table shipped to Python.
* **Words.** `memories.content_search` is a generated `tsvector` with a GIN
  index, so a memory is searchable the moment it lands with no second write
  to forget. It is capped at the first 100,000 characters, because a tsvector
  is hard-limited to 1MB and a generated column that raises fails the INSERT
  and loses the memory outright — an unfindable memory is recoverable and a
  refused one is gone.

The text configuration is neither `simple` nor stock `english`, and the
reason is that FTS5 is configured `porter unicode61`. So it **stems** (the
live index holds `rotat` and no `rotation`, 1,151 rows of it), it **folds
diacritics** (`jose` finds `José`, and 4,097 rows carry non-ASCII bytes), and
it removes **no stopwords** — FTS5 indexes every token, and lucent filters
its own stoplist out of the query instead. Stock `english` would strip
stopwords from the documents too and stop matching query words that stoplist
keeps.

Two things about the ported blend are worth knowing before reading a score.
Postgres has no BM25, and `ts_rank` is not a rescaled BM25 — it is bounded
below 1 where `bm25()` is unbounded, so no single multiplier maps one onto
the other for every query. Measured over the live corpus the ratio runs from
about 90 to about 540; `KEYWORD_SCALE` is the median, because the alternative
is not "no scaling" but a silent change of magnitude in two places that both
matter: the figure is added to the combined score with a fixed coefficient,
and it is rendered as `bm=` into every mind's injected context every turn.
Within a factor of two of the old magnitude is the goal; exact is not
available. The report prints the per-query ratio so the constant can be
checked rather than believed.

And the pool sizes, the slot allocation and the decay are lucent's own
constants, carried across unchanged — including one that is carried
deliberately rather than approvingly: the keyword candidate limit is applied
across the whole store and the provenance filter after it, so a mind holding
few rows gets fewer candidates than the pool is sized for. Filtering first
is a better answer and a different one, which a story that ports the blend
unchanged does not get to make.

`memory.tables` and `memory.rows` are the console's memory browser rather
than part of recall: the table listing with a row count each, and one page of
any one of them. Read from the database's own catalogue, scoped to this
schema, which is what the SQLite browser did through `sqlite_master` and
`PRAGMA table_info` — so a table added to the memory schema appears on the
page instead of being invisible until somebody declares it, and the
identifier on the request is only ever used after it has been matched against
that catalogue. Two things the port had to decide rather than transcribe. A
`vector`, a `tsvector` and a `bytea` are summarised in the database — `<vector
4096 dims>` — so 4096 floats a row never cross the wire, which is what
`<BLOB n bytes>` did for the same reason. And the page is ordered by the
table's primary key: the old browser named no order and got away with it,
because an unordered scan of a SQLite rowid table comes back in rowid order
in practice, while Postgres promises nothing and the same query may use a
different plan on the second call — so paging without an order repeats some
rows and skips others, which on a browser built to check a load is the one
failure that reads as a bad load.

`docs/memory-search-parity.md` is the measured comparison, taken before the
cutover against a snapshot of the SQLite store, with both engines scoped the
way the live caller scoped them and one embedding per query handed to both
sides. The tool that produced it read the retired store and is gone; the
report stays as the record the scaling constant was set from.

An install that runs none of this is unaffected. A database with no `memory`
schema opens normally — that is comms, which needs `core` and nothing else —
and the first memory operation such a process calls says the schema is not
there rather than implying a refused write.

## The board

`hive_data.board` is the console's own context: the Kanban board every epic,
feature and story in the hive lives on, the design sessions whose three pages
are read before any code is written, the notices that carry a submission back
to a mind, and two small settings tables.

Three things in it are not a transcription of the SQLite module it replaces.

**The order has a tie-break that exists.** Every board read was
`ORDER BY position, rowid`, and Postgres has no `rowid`. Ties break on `id`
instead, which decides nothing the old order decided — `position` is unique
within a parent on the loaded board, so sibling order is settled by
`position` alone, and the only ties are between rows under *different*
parents in a flat listing every consumer regroups by parent. What it buys is
that the flat listing is the same list twice in a row, which
`ORDER BY "position"` on its own does not promise.

**The cascade is the database's.** The SQLite module walked the tree in
Python and deleted the whole frontier in one statement, because SQLite's
`foreign_keys` pragma is off by default and per connection — so a declared
cascade was decorative on any connection that forgot it, and the orphans it
left still rendered on the board while being unreachable from the only
delete button. Here the key is real, so `delete_subtree` is one recursive
statement.

**The deferred key is honoured rather than worked around.**
`work_items.parent_id` is `DEFERRABLE INITIALLY DEFERRED`, so a child may be
written before its parent inside one unit of work — which is what a loader
restoring a subtree needs. The cost is stated rather than hidden: a
`parent_id` naming nothing at all is refused at the *commit*, as a
`MissingReference` out of the `async with` and not out of the operation.
Nothing sets the constraints back to `IMMEDIATE` to move that error earlier,
because doing so would also refuse the legitimate out-of-order write.

Changing what an item *is* is `board.retype`, its own operation rather than
a settable `kind` on `update_work_item`. A retype is one fact made of five
columns and every one of them follows from the new kind: an epic has no
status and a story has one, a bug is a story carrying the bug subtype, a row
becoming an epic loses its parent, and a row that moves parents needs a
position because the number it held was only unique under the parent it left.
Written one column at a time the board is briefly a feature with a story's
status, or a row at a duplicate number, and the console reads it in between.
`update_work_item` is deliberately left unable to do it: the title, the prose
and the status are the operator's to edit from a form, and the kind is not
something a form field sets in passing.

Every reordering write takes `board.hold_board(unit)` first. Each one reads
the sibling list, decides a new numbering against it and writes the whole
list back, so two interleaved is one tab's drag silently replaced by the
other's — with both told they succeeded and two siblings left holding one
position. Postgres offers no equivalent of SQLite's file-wide write lock and
row locks are no help, because the rows a reorder will renumber are not known
until it has read them.

`board.notice` reads one notice by id whatever state it is in, which the
delivery path's own listing cannot: that answers only undelivered ones, so a
caller holding an id gets nothing back and cannot tell "delivered" from
"never existed". `core.put_auth_setting_if_absent` is the console minting its
cookie-signing key on first use, as one statement — two workers reaching an
empty install at once would each generate a key and each write it, and
whichever landed second would sign every later cookie and invalidate the ones
the other had already issued, which presents as the whole install being
signed out. The `DO UPDATE` is a no-op write of the value already there,
because `DO NOTHING` returns no row when the key exists and leaves the caller
reading it in a second statement — the race this exists to close.

`board.operation_requesters` is the fifth table and the console created it on
demand, having never been asked: it reached the cutover with no rows and no
home in the new database. It is carried rather than dropped because the two
routes that write and read it are live — a gated hive-tools answer carrying a
request id is recorded against the signed-in user, and that operation's
status is then only theirs to read. Recording the same request id twice keeps
the later name instead of refusing the write, because a tool reporting one id
twice is a replay or a re-POSTed webhook on a path whose whole job is
bookkeeping.

The derived backlog numbers are `board.backlog_numbers`, and they answer what
the console answers today — including two cases that are arguably wrong and
were carried over regardless, because every story's number appears in
conversations, commit messages and the lucent graph, and a port that
renumbers the board is a port that renames work. An **epic** numbers as a
root whatever `parent_id` holds, and a **story under a story** does too.
The evidence was a parity run that copied the console's own board into a
scratch database and compared the two implementations row for row: 646
rows, zero numbers differing. It read the console's retired SQLite file and
was deleted with it.

## Applying the schema

```
python -m hive_data.migrate check --dsn D   # writes nothing
python -m hive_data.migrate apply --dsn D
```

`--dsn` defaults to `HIVE_DATABASE_URL`, and both are importable as
`await hive_data.migrate.check(dsn)` and `await hive_data.migrate.apply(dsn)`.
Each prints one JSON object on stdout and each problem on its own line on
stderr. `check` exits 0, or 2 with every reason `apply` would refuse: the
`vector` or `unaccent` extension missing from the server, a role that may not
add one (`vector` is not trusted, so only a superuser can; `unaccent` needs
CREATE on the database; both go in `public`, which on Postgres 15 and later a
non-owner may not create in), no CREATE on the database (for a baseline
schema or a later step's `CREATE SCHEMA`), a later step's foreign key into an
existing table the role holds no REFERENCES on, a step creating a role
the migrating role may not create (no CREATEROLE), a schema holding
only some of its tables, or a record of a step newer than this package
knows. `apply` runs the same check first and writes nothing when it fails
(exit 2); a step the database refuses is exit 1, naming the step.

The schema is a numbered list of steps. Steps 1 to 4 are the four baseline
files, `core`, `memory`, `tools` and `board`, in that order because `board`
has foreign keys into `core`. A schema change from here on is a new file
`hive_data/schema/steps/NNNN_name.sql` with a number above 4, never an edit
to a baseline file: a hive that already ran the baseline would never see the
edit. Each step runs in one transaction with the row that records it in
`hive_meta.migrations`, so a step is applied and recorded or neither, and a
run that fails starts at that step next time.

A database the hive reached before the record existed — the hive this
package was written against — is *adopted*: a baseline step whose schema
holds every table declared in `hive_data.schema` is recorded without running.
That is the meaning of "present" here, and deliberately not `verify()`'s,
which lets a database with no `memory` schema open because comms needs only
`core`. So an empty database gets all four steps, one holding only `core` has
the other three run, a current hive is a no-op, and a newer step is the only
thing run on a hive that has the rest.

## The chief of staff's role

Step 7 makes `hive_staff`, a NOLOGIN role that may connect, use the `staff`
schema and read and write its tables, and read or write no other schema's
tables. It keeps what every role has from PUBLIC (CONNECT and TEMP, unless
the server revoked them). The database's CONNECT grant needs a migrator that
owns the database; for one that does not, Postgres reduces it to a warning
and PUBLIC's CONNECT is what lets the login in. The chief of
staff holds the hive's widest reach over conversations, so its database
credential is the narrowest one there is. The login carrying a password is
not in a step — a role is cluster-wide and a password is not a tracked
value — and is made once per hive, as a superuser, by piping this to `psql`
on stdin so the password stays off every command line:

```
CREATE ROLE stash LOGIN PASSWORD '<generated>' IN ROLE hive_staff;
```

Its URL is that mind's `HIVE_DATABASE_URL`; for the hive's `stash`
container, `STASH_DATABASE_URL` in hive_mind's `.env`, which its compose
fragment passes in. That role sees only `staff`, so
`hive_data.connect()`'s schema check, which reads every schema, is passed
`verify=False` by a process connecting as it.

## Scope

This package covers the `core`, `memory`, `tools`, `board` and `staff`
schemas. `staff` (step 6) is the chief of staff's ledger: `staff.tasks`, a
`staff.statuses` lookup its status is a foreign key into, and
`staff.task_sessions` pairing a task with the `core.sessions` ids working it
(not a foreign key: the pair outlives comms deleting an ended session).
`hive_data.staff` is the only way the chief of staff and its tick reach it.

Two things are deliberately outside it. **hive-health** is not part of the one
database at all. The **inference proxy** keeps SQLAlchemy and its own store:
all six of its foreign keys are internal to its own schema, nothing else in
the hive reads its tables (the gateway and the minds get models over HTTP from
`/v1/models`), and it is a separately deployed product being replaced by a
more mature one. It is also the only service using an ORM, which is why this
package needs no ORM face.

## Tests

```
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"
.venv/bin/python -m pytest
```

The suite creates a database of its own per run and drops it afterwards — never
the live `hive` database, whose rows are the pre-cutover copies the loader
story still has to verify row for row. It applies the
schema through `hive_data.migrate` (below), exactly as an install does. The
baseline is `hive_data/schema/core.sql`, `memory.sql`, `tools.sql` and
`board.sql`, one file per schema, kept in the package. They began as
`pg_dump -s` output of the schemas as first applied; the generator that
produced that is deleted with the SQLite stores it read. One artifact per schema rather than one for the
database, because a deployment can decline to create a context it does not
run — comms needs `core` and nothing else — and because the memory one needs
the `vector` extension, which is not a trusted extension and so needs a
superuser to install. `board.sql` is applied after `core.sql` and not before
it: `board.design_sessions` has real foreign keys into `core.sessions` and
`core.minds`, which is the first thing in this database that could not exist
while each store was its own SQLite file.

`HIVE_DATA_TEST_ADMIN_DSN` points it at a server, with no default, because a
default would be a credential in a tracked file. The suite skips cleanly
without it, and sweeps any database a killed run left behind. The default is the hive's
Postgres on its container network rather than loopback, and that is
load-bearing for one test: `pg_hba.conf` trusts loopback and demands scram
from everywhere else, so a wrong password over loopback *succeeds* and the
refused-credential test would pass for the wrong reason.

Several runs against one server is the normal case — three reviewers each
running pytest during a grill — so every scratch database a run creates is
*claimed*: a session-level advisory lock held on one connection for as long
as the database is wanted, keyed by the database's own name and taken before
the `CREATE`. A sweep drops only what it can take the claim for. Deciding
idleness by counting backends instead does not work, because a run's own
database has no connections to it between tests: the pool fixture opens one
per test and closes it again, so the question is answered "nobody" about a
database in active use and the owning run loses every remaining test to
`database "..." does not exist`. See `tests/_scratch.py`.
